# FlowOrder V6.1.3 部署、Coze联调与验收操作手册

> 基线：当前线上 V6.1.2 代码仓库  
> 目标版本：V6.1.3  
> 原则：保留“10个原子工具＋2个组合工具＋Coze Agent编排”，只修确定性规则、状态表达、结果口径和可审计性。

---

## 一、本轮优化到底改了什么

### 1. 业务规则修复

- 日期型供应商完工承诺按“自然日”判断：承诺当天尚未逾期，第二天才算逾期。
- 带具体时分的承诺回复时间仍按精确时间判断。
- 同一订单的多种异常聚合为一笔订单结果，最多返回7笔不同订单。
- `INFORMATION_GAP`单独统计，不进入风险榜，不用于凑满Top 7。
- 真实风险只有5笔时只返回5笔。

### 2. Agent页面优化

- 明确区分：后端服务、Coze Agent、定时巡检接口。
- Coze Agent未配置时，Agent按钮禁用；规则巡检仍可手动执行。
- Agent调用失败后不再静默替换成规则结果。
- 用户输入框只写业务目标，系统约束改为可视化设置。
- “本次运行”和“历史累计”分开统计。
- 新增可审计轨迹：运行ID、工具调用、任务草稿ID、审批ID、停止原因。

### 3. Agent架构保持不变

保留：

```text
用户开放目标
→ Coze Agent理解意图
→ 选择组合工具或原子工具
→ 根据结果决定追问、停止、生成任务或发起审批
→ 人工确认正式动作
```

没有把Agent改成普通规则系统，也没有删除原子工具。

# 二、部署前必须做的备份

## 步骤1：记录当前线上版本

1. 浏览器打开：

```text

```

2. 截图保存，确认当前显示：

```json

  "status": "ok",
  "version": "6.1.2"
}
```

3. 再打开：

```text
https://你的Railway域名/api/v61/status
```

保存截图。

## 步骤2：GitHub创建备份分支

1. 打开当前Railway实际部署的GitHub仓库。
2. 点击分支下拉框。
3. 输入：

```text
backup-before-v6.1.3
```

4. 选择“Create branch from main”。
5. 确认备份分支已经出现。
6. 切回Railway当前部署分支，一般为`main`。

## 步骤3：备份Coze配置

在Coze中分别保存：

1. 当前Agent“人设与回复逻辑”全文；
2. 当前已发布Agent的Bot ID；
3. 当前插件列表截图；
4. 当前12个工具名称截图；
5. 插件鉴权Header配置截图；
6. 当前Agent发布版本截图。

## 步骤4：备份Railway变量与持久卷

在Railway项目中：

1. 打开 Variables；
2. 截图变量名称，不要暴露变量值；
3. 确认存在持久卷挂载：

```text
/data
```

4. 确认变量：

```text

```

5. 记录当前Deployment ID和提交哈希。

# 六、V6.1.2遗留问题专项回归

## 用例A：日期型承诺当天不算逾期

### 准备数据

找一笔未完成订单，设置：

```text
工厂完成承诺：今天
当前进度：45%
```

例如当前日期为2026-08-03：

```text
工厂完成承诺：2026-08-03
```

### 执行

运行规则巡检。

### 正确结果

订单可能因为交期风险进入榜单，但证据中不能出现：

```text
供应商完工承诺2026-08-03已过期
```

### 反向测试

把承诺改成昨天：

```text
2026-08-02
```

重新巡检，证据中应出现供应商承诺已过期。

---

## 用例B：具体时间的回复承诺仍按时分判断

准备一个等待任务：

```text
承诺回复时间：今天15:00
当前时间：今天16:00以后
```

正确结果：应识别为承诺回复超时。

如果当前时间为14:00，则不能报超时。

---

## 用例C：同一订单多异常只占一个排名

准备一笔订单同时满足：

```text
客户交期临近或已超期
供应商承诺已过期
当前进度偏低
```

正确结果：

```text
订单在Top榜只出现一次
主要异常：一项
次要异常：至少一项
共识别2类或更多异常
```

不能在Top榜中重复出现同一订单号。

---

## 用例D：信息缺口不进入风险Top 7

准备一笔订单：

```text
客户交期约10天后
当前进度约90%
当前节点为空
没有承诺超时
没有高风险任务
```

正确结果：

```text
该订单出现在“信息缺口”区域
不出现在“风险订单Top N”区域
```

---

## 用例E：不足7笔不补齐

让当前可见真实风险订单少于7笔。

正确结果：

```text
真实风险5笔 → 返回5笔
真实风险2笔 → 返回2笔
真实风险0笔 → 返回0笔
```

不能加入信息缺口或低价值记录凑满7笔。

# 七、更新Coze Agent系统提示词

后端规则测试通过后，再连接Coze。

## 步骤1：打开Coze Agent

1. 进入当前FlowOrder Agent；
2. 打开“人设与回复逻辑”；
3. 全选旧内容并复制到备份文档；
4. 打开补丁文件：

```text
coze/AGENT_SYSTEM_PROMPT_V6_1.md
```

5. 复制全文覆盖到Coze。

## 步骤2：检查关键条款

确认新提示词包含：

```text
后续所有工具必须传同一个run_id
INFORMATION_GAP不进入风险Top 7
严格遵守start_agent_run返回的工具次数和时间预算
真实风险不足7笔不补齐
日期型承诺当天尚未逾期
规则巡检不得冒充Coze Agent结果
```

## 步骤3：不要同时保留两套冲突规则

删除旧提示词中以下固定表述：

```text
最长分析60秒
返回7个异常候选
信息缺口可进入Top 7
```

最终时间预算以`start_agent_run`返回值为准。

# 八、Coze插件处理方式

## 推荐方案：现有12工具插件正常时不要重建

如果当前12个工具已经能成功调用：

- 不删除插件；
- 不重复导入；
- 不修改operationId；
- 不新建同名工具。

V6.1.3接口路径和主要请求结构没有变化，现有插件可以继续调用。

## 需要重建插件的情况

只有出现以下问题才重建：

```text
插件只有10个工具
组合工具不存在
插件服务域名已变
工具返回始终为空对象
鉴权Header无法传递
```

### 重建步骤

1. 先删除旧的重复插件，避免同名工具冲突；
2. 使用：

```text
coze/floworder_agent_plugin_openapi_12tools_railway.json
```

3. 打开JSON，确认`servers.url`等于当前Railway公网域名；
4. 如果域名不同，先修改JSON中的URL；
5. 导入后确认共12个工具；
6. 配置固定Header：

```text
X-FlowOrder-Agent-Key
```

值必须与Railway中的：

```text
FLOWORDER_AGENT_API_KEY
```

一致；
7. 不要把真实密钥写进GitHub文件；
8. 分别测试：

```text
start_agent_run
diagnose_priority_orders
create_task_draft
create_approval_request
complete_agent_run
```

# 九、发布Coze Agent并连接Railway

## 步骤1：发布Agent

1. 保存提示词；
2. 确认插件已绑定；
3. 点击发布；
4. 选择允许API调用；
5. 记录正式Bot ID。

## 步骤2：准备Coze API Token

在Coze官方控制台创建可调用Agent的Token。

不要：

- 写进代码；
- 上传GitHub；
- 发到聊天；
- 放进截图。

## 步骤3：Railway配置变量

在Railway Variables中设置：

```text
COZE_API_TOKEN=<真实Token>
COZE_AGENT_BOT_ID=<正式Bot ID>
COZE_API_BASE=https://api.coze.cn
FLOWORDER_AGENT_API_KEY=<插件调用后端的密钥>
FLOWORDER_CRON_API_KEY=<定时巡检接口密钥>
FLOWORDER_AGENT_MAX_TOOL_CALLS=8
FLOWORDER_AGENT_MAX_DURATION_SECONDS=120
COZE_AGENT_TIMEOUT_SECONDS=120
DB_PATH=/data/action_layer.db
```

变量名必须完全一致。

## 步骤4：重新部署

保存变量后Railway会重新部署。

部署完成后打开：

```text
/api/agent/status
```

期望：

```json
"coze_agent": {
  "configured": true,
  "state": "CONFIGURED"
}
```

网页应显示：

```text
Coze Agent：已配置
```

注意：“已配置”表示凭证和Bot ID存在；真正连通仍需执行一次Agent诊断验证。

# 十、Agent模式端到端验收

## 步骤1：发起业务目标

在异常诊断页输入：

```text
检查我未来14天内最需要处理的订单。
```

设置：

```text
最多返回：7笔
生成任务草稿：开启
需要正式动作时创建审批：开启
```

点击：

```text
启动Agent诊断
```

## 步骤2：检查最终回答

回答应包含：

```text
分析范围
扫描订单数
真实风险订单数
异常信号数
信息缺口数
每笔订单证据
建议动作
是否需要人工确认
```

如果创建了任务和审批，还应返回：

```text
task_draft_id
approval_id
```

没有真实ID时，不能声称已经创建。

## 步骤3：刷新查看执行轨迹

点击浏览器刷新，重新进入异常诊断页。

轨迹应尽量出现：

```text
start_agent_run
diagnose_priority_orders
create_task_draft
create_approval_request
complete_agent_run
```

至少要有：

```text
run_id
工具调用记录
停止原因
```

任务草稿和审批调用成功时，轨迹中应显示真实ID。

## 步骤4：验证不静默降级

临时清空或填错`COZE_AGENT_BOT_ID`，重新部署后点击Agent按钮。

正确结果：

```text
Agent按钮禁用，或明确提示Coze未配置
```

不能自动展示规则巡检结果并冒充Agent回答。

恢复正确变量后重新部署。

# 十一、任务草稿和审批验收

## 任务草稿

Agent可生成草稿，但不能直接创建正式任务。

检查：

```text
task_draft_id存在
正式任务数量未自动增加
```

## 审批请求

检查：

```text
approval_id存在
状态为PENDING
页面显示待人工或待主管
```

正式订单字段、外发消息、延期、费用和赔偿仍不可自动执行。

# 十四、出现问题时怎么定位

## 页面仍显示V6.1.2

1. 检查GitHub提交是否在Railway部署分支；
2. 检查Railway最新Deployment提交哈希；
3. 强制刷新；
4. 查看`static/index.html`是否引用：

```text
app.js?v=6.1.3
styles.css?v=6.1.3
```

## Agent显示未配置

检查Railway变量名：

```text
COZE_API_TOKEN
COZE_AGENT_BOT_ID
```

检查变量值是否含多余引号或空格。

## Agent返回401

检查Coze插件Header：

```text
X-FlowOrder-Agent-Key
```

是否和Railway变量`FLOWORDER_AGENT_API_KEY`一致。

## Agent超时

1. 确认优先调用`diagnose_priority_orders`；
2. 不要逐笔循环调用四个原子诊断工具；
3. 确认所有工具传同一个`run_id`；
4. 检查Railway冷启动；
5. 检查`COZE_AGENT_TIMEOUT_SECONDS=120`；
6. 查看运行轨迹中最后成功工具。

## 审批已创建但Agent没返回ID

1. 用`run_id`查看：

```text
/api/agent/runs/<run_id>/trace?current_user_id=USER-1&current_role=operator
```

2. 检查`approval_ids`；
3. 检查网站待审批列表；
4. 不要重复点击创建，审批接口有幂等保护。

# 十五、回滚方法

## GitHub回滚

切回：

```text
backup-before-v6.1.3
```

或Revert V6.1.3提交。

## Railway回滚

在Deployments中选择V6.1.2最后成功部署，点击Redeploy。

## Coze回滚

1. 恢复备份的旧提示词；
2. 重新发布；
3. 不需要删除数据库；
4. 不要更换Agent工具密钥，除非怀疑密钥泄露。

V6.1.3没有破坏性数据库迁移，代码回滚不需要清空SQLite。
